
功能性需求:
制作一个知识库web应用, 用于提供llm对话功能和知识库管理, 该系统应该提供以下能力:
1. llm对话:
   - 提供一个页面, 用于和大语言模型对话
   - 用户可以自定义提示词, 且该提示词可以复用
   - 用户可以选择将对话内容保存为md文档, 并上传的指定知识库的指定目录中
   - 对话可以选择某个知识库(或不选择), 基于rag进行增强对话
   - 用户可以查看对话历史, 并查看对话详情(包括对话内容, 时间, 对话来源知识库等)
   - 用户可以选择对话时使用的模型, 模型信息在系统配置中配置
2. 知识库管理:
   - 用户可以创建多个知识库, 创建时可以选择系统配置中已配置好的嵌入模型和重排序模型及其他于文章分段相关的参数
   - 用户可以上传文件(支持批量)和文件夹到知识库的指定目录中, 系统会自动将文件进行分段并上传至索引库
   - 用户可以查看知识库的目录树, 并查看文件详情(包括名称, 路径, 上传时间, 文件大小等)
   - 针对知识中的某个文件, 用户可以查看文件内容
   - 针对某个知识库, 用户可以执行搜索操作, 系统会返回搜索结果, 搜索结果应该包含文件名, 路径, 文件大小, 文件内容片段等信息
   - 用户可以上传同名文件覆盖已有文件, 系统会重新解析该文件, 同时支持文件的删除操作
3. 智能推荐:
   - 文件上传和修改的权重不同, 修改应该综合上传时间, 然后系统根据**记忆曲线**智能推荐阅读文章
   - 借助llm的能力, 可以基于用户历史行为进行推荐
   - 设置相应的目标帮助用户进行回顾
   - 作为系统初始页展示给用户
4. 系统配置:
   - 提供模型参数配置, 模型分为对话模型(在llm对话中使用)、嵌入模型(用于知识库管理)、重排序模型(用于知识库管理)、文章分段模型(用于知识库管理); 并可以配置它们的详细参数
   - 用户在创建知识库时可以选择使用系统配置中已配置好的嵌入模型和重排序模型, 也可以在之后修改模型, 系统将进行重新索引
   - 上述的每类模型都可以配置多个在使用时选择
   - 每种模型可以选择一个作为默认值
   - 提供智能推荐系统的相关配置
   - 设置中提供全局的导入导出功能
   - 提供mcp配置接口, 可以将mcp服务动态添加到服务中在对话时使用(低优先级)
5. 用户管理:
   - 用户注册和登录
   - 用户可以修改密码
   - 用户可以修改用户信息
   - 上述所有功能都与用户关联
   - 分布式场景需要考虑认证


非功能性需求:
- 后端:
  - 使用springboot + kotlin + postgresql(同时作为向量数据库) + redis + mcp + kafka(消息总线)
  - 使用微服务架构 拆分方式为横向按照功能进行模块化拆分, 如拆分为用户, 知识库等功能
  - 使用ddd的方法论进行开发, 会使用事件风暴完成完成战略设计和战术设计, 期间会输出完整的领域模型(使用plantuml的形式输出 uml元素可以参考 single.puml ) 之后会使用六边形架构进行开发
  - 使用CQRS和saga事务模型等模式保证项目的工程化
  - 使用编码型事务保证数据一致性
    - 其中每个功能分为两个模块, 分别为领域模块和应用模块, 如用户功能分为lifee-user(领域模块 内六边形)和lifee-user-app(应用模块 外六边形)
      - 领域模块: 主要保存事件风暴建模后输出的模型,命令,事件,事件处理器等(只关心业务)
        内六边形（领域层）
      ```
        ├── 聚合根 - 业务逻辑封装
        ├── 实体 - 领域对象
        ├── 值对象 - 不可变概念
        ├── 领域事件 - 业务变更表达
        └── 仓储接口 - 出站端口定义
      ```
      - 应用模块: 主要提供用户界面, 接口, 逻辑处理, 集成其他服务
       ```
        外六边形（基础设施层）
        ├── JPA实体 - 数据持久化适配器
        ├── 仓储实现 - 数据访问适配器  
        ├── REST控制器 - Web适配器
        └── 外部服务客户端 - 集成适配器
      ```
      - 命令端调用流程
      ```
        HTTP请求 → Controller → service(是否需要自行决定) → CommandBus → CommandHandler → AggregateRoot → DomainEvent → EventBus
      ```
      - 查询端调用流程
      ```
        HTTP请求 → Controller → service(是否需要自行决定) →  QueryBus → QueryHandler → Repository → ReadModel → HTTP响应
      ```
  - 测试: 要求覆盖90%的单元测试, 使用行为驱动开发, 使用jest进行单元测试, 使用playwright进行集成测试, 使用sonarqube进行代码质量检测
  - 使用gitlab ci/cd进行持续集成和持续部署, 使用prometheus和grafana进行监控, 使用opentelemetry进行分布式追踪
  - 前端使用react + typescript + nextjs + Tailwind + vite, 可以基于模版项目 `https://github.com/ibelick/zola.git` 开发
- 保证系统的安全性和可用性, 系统应该是易拓展的
